# חוות אייג'נטים

## מה הרכיב עושה

מאפשר לשלוח תת-משימה של משימת פיתוח לאייג'נט שעובד על המחשב של המשתמש: Claude Code לפרויקטים של העבודה, Codex לפרויקטים אישיים. האייג'נט עובד בתיקייה ובענף משלו, ומדווח בחזרה ללוח. הסטטוס של תת-המשימה זז איתו: כשהאייג'נט עובד היא "ממתין לתגובה", וכשהוא מסיים (או נכשל) היא "בעבודה אצלי". משימות שאינן משימות פיתוח לא משויכות לאף פרויקט, ולא משתנה בהן כלום.

שלושה חלקים:

```
הלוח (דפדפן / נייד)  --insert job-->  Supabase: agent_jobs (תור)  <--claim / report--  ראנר על מחשב הפיתוח
        ^                                     |                                          |
        +------ realtime: סטטוס, סיכום -------+                         claude -p / codex exec בתיקיית העבודה
                                              agent_runners (heartbeat + רשימת פרויקטים)
```

האתר הוא אתר סטטי ואין לו דרך להריץ משהו במחשב. לכן הראנר (`runner/`) הוא תוכנית Node נפרדת שרצה ברקע על מחשב הפיתוח. הוא מתחבר עם אותו חשבון כמו הלוח, ומקבל רק עבודות שמיועדות למחשב שלו.

## הטבלאות בענן

**`agent_runners`** - שורה לכל מחשב שהראנר רץ עליו: `id` (uuid שהראנר יוצר ושומר מקומית), `user_id`, `name`, `projects` (מערך JSON של `{ key, name, engine, profile }` - בלי נתיבים), `started_at`, `last_seen_at`. ה-trigger `agent_runners_touch` קובע את `last_seen_at` לפי השעון של מסד הנתונים. מחשב נחשב מחובר אם דיווח ב-3 הדקות האחרונות (`RUNNER_ONLINE_MS`); הראנר מדווח כל דקה.

**`agent_jobs`** - שורה לכל הודעה לאייג'נט:

| עמודה | תוכן |
|-------|------|
| `id`, `user_id` | uuid (הלוח יוצר אותו), בעלים |
| `runner_id`, `project_key` | לאיזה מחשב ולאיזה פרויקט |
| `task_id`, `subtask_id` | המשימה ותת-המשימה בלוח |
| `prompt` | ההודעה (עד 20,000 תווים) |
| `status` | `queued` -> `running` -> `done` / `failed` / `cancelled` |
| `cancel_requested` | הלוח ביקש לעצור עבודה שרצה |
| `summary`, `error` | התשובה של האייג'נט (עד 8,000) והשגיאה (עד 2,000) |
| `branch`, `worktree_path`, `changed_files` | איפה האייג'נט עבד וכמה קבצים השתנו |
| `created_at`, `started_at`, `finished_at`, `updated_at` | נקבעים על ידי ה-trigger |

אבטחה ושלמות:
- RLS: כל משתמש רואה ומשנה רק את השורות שלו; ל-`anon` אין הרשאות.
- מדיניות ה-insert מאפשרת ליצור רק עבודה `queued` נקייה (בלי תשובה ובלי בקשת עצירה).
- ה-trigger `agent_jobs_guard` מונע שינוי של מה שהעבודה מבקשת אחרי שנוצרה (משתמש, מחשב, פרויקט, משימה, הודעה), מונע חזרה אחורה (סטטוס סופי לא משתנה, ו-`running` לא חוזר ל-`queued`), וקובע את הזמנים.
- שתי הטבלאות בפרסום `supabase_realtime`.
- הראנר מוחק בהפעלה עבודות סגורות שלו שנוצרו לפני יותר מ-60 יום.

## הזרימה בלוח

1. **שיוך**: בחלון המשימה, השדה "אייג'נט" מציג את הפרויקטים שהמחשבים מציעים (שם, מנוע, פרופיל, "לא מחובר", "הגדרות סותרות"). הבחירה נשמרת ב-`task.agentProject` (פעולה `task/update`). "בלי - משימה רגילה" מבטל את השיוך. אם אותו מפתח מוגדר במחשבים שונים עם מנוע או פרופיל שונה (`isMismatched`), לא נשלח אליו כלום, כדי שמשימת עבודה לא תגיע למחשב שבו אותו מפתח פירושו החשבון האישי.
2. **שליחה**: במשימה משויכת, ליד כל תת-משימה יש כפתור אייג'נט שפותח את חלון האייג'נט. `pickRunnerForJob` בוחר את המחשב שהריץ את העבודה הקודמת של המשימה אם הוא מחובר (שם נמצאים השיחה והתיקייה), אחרת את המחובר שנראה אחרון. השיחה נשמרת לפי משימה בכל מחשב, ולכן `promptContextFor` קובע כמה הקשר לצרף (`composeAgentPrompt`): `task` - המחשב עוד לא ראה את המשימה (כותרת, תיאור ותת-המשימה); `subtask` - תת-משימה חדשה בשיחה קיימת (רק "מה לעשות עכשיו"); `none` - המשך של אותה תת-משימה (ההודעה כמו שנכתבה, וחובה לכתוב משהו).
3. **מתי אי אפשר לשלוח** (`agentSendBlocker`): הטבלאות לא קיימות, הרשימה עוד נטענת, המשימה לא משויכת, אף מחשב עם הפרויקט לא מחובר, הפרויקט מוגדר אחרת במחשבים שונים, או שהאייג'נט עוד עובד על ההודעה הקודמת של תת-המשימה.
4. **מעקב**: `agent-hub.js` טוען את המחשבים ועד 300 עבודות אחרונות כשהערוץ החי מתחבר (וגם כשהוא מתחבר מחדש), ואחר כך העבודות מתעדכנות דרך realtime. כל דקה נטענת מחדש רק רשימת המחשבים (שורות קטנות), כדי שלוח שפתוח כל היום לא יוריד שוב ושוב את כל ההודעות. עותק של עבודה שמגיע מאוחר (תשובה לבקשה שיצאה לפני עדכון realtime) לא מחזיר אותה לשלב קודם (`laterCopyOfJob`). אחרי כל שינוי, `reconcileAgentJobs` מריץ את `agentSyncActions`: לכל תת-משימה שהעבודה האחרונה שלה חדשה יותר (או מתקדמת יותר) ממה שהמסמך מכיר, נשלחת פעולה `subtask/agentSync`. זה קורה רק אחרי שהמשימות של החשבון נטענו (`isSyncReady`), וגם אחרי קבלת עותק מהענן.
5. **ביטול**: עבודה בתור מבוטלת מיד (עדכון מותנה ב-`status = 'queued'`). עבודה שרצה מקבלת `cancel_requested`, והראנר עוצר את האייג'נט ומדווח "בוטל". אם המחשב שמריץ אותה לא מחובר (למשל התיקייה המקומית שלו אבדה והוא קיבל מזהה חדש), מופיע "סגירת הריצה": אחרי אישור העבודה נסגרת כ-`cancelled` מהלוח (`cancelJob(id, { close: true })`). אם המחשב יחזור ויסיים, הדיווח שלו לא יתאים לעבודה פתוחה ולא יירשם.

### מיפוי לסטטוס (`subtaskStatusForJob`)

| מצב העבודה | הסטטוס של תת-המשימה |
|------------|----------------------|
| `queued` (נשלח) | ממתין לתגובה - תמיד, גם אם תת-המשימה הייתה "הושלם" (שליחה מחדש פותחת אותה) |
| `running` | ממתין לתגובה, אלא אם בינתיים סומנה "הושלם" |
| `done` / `failed` / `cancelled` | בעבודה אצלי ("תורך"), אלא אם בינתיים סומנה "הושלם" |

`subtask.agentJob = { id, status, createdAt }` שומר את המצב האחרון שהוחל. עדכון ישן (עבודה ישנה יותר, או מצב שהעבודה כבר עברה) הוא no-op (`isNewerJobState`; שתי עבודות שנוצרו באותה מילישנייה מסודרות לפי id, זהה בכל מכשיר), ולכן כמה מכשירים פתוחים ו-replay של הסנכרון מגיעים לאותה תוצאה. שינוי ידני של הסטטוס אחר כך לא נדרס, כי הסנכרון פועל רק כשמצב העבודה משתנה.

### הממשק

- **ריבוע**: רובוט קטן ליד הקטגוריה במשימה משויכת; רובוט ליד תת-משימה פתוחה שיש לה עבודה (מהבהב בזמן שהאייג'נט עובד, בצבע המצב).
- **חלון המשימה**: השדה "אייג'נט" (מוצג כשהטבלאות זמינות, או כשהמשימה כבר משויכת), וכפתור לכל תת-משימה עם מצב העבודה האחרונה ("לאייג'נט", "ממתין בתור", "האייג'נט עובד", "סיים - תורך", "נכשל", "בוטל").
- **חלון האייג'נט** (`agent-dialog`): תת-המשימה, הפרויקט והמחשבים (נקודה ירוקה = מחובר), השיחה (ההודעות שלי והתשובות, מצב, כמה זמן הוא עובד, ענף, מספר קבצים, "פתיחה ב-VS Code" דרך `vscode://file/...`, ביטול או עצירה), ותיבת הודעה סטטית ב-HTML - עדכונים מהאייג'נט לא מוחקים טקסט שמקלידים. Ctrl+Enter שולח. השיחה גוללת לסוף רק אם המשתמש כבר היה בסוף.
- **הגדרות -> אייג'נטים**: כל מחשב, מחובר או "נראה לאחרונה לפני...", והפרויקטים שלו. כשהטבלאות לא קיימות מוצגת הנחיה להריץ את `supabase/schema.sql`.
- צבעי מצב העבודה (`--job`): בתור אפור, עובד ענבר (כמו "ממתין"), סיים כחול (כמו "אצלי"), נכשל אדום.

## הראנר

### הפקודות

| פקודה | מה עושה |
|-------|---------|
| `npm run runner:login` | התחברות עם אותו חשבון כמו הלוח (אימייל + סיסמה מוסתרת). נשמר רק ה-session, ב-`auth.json` בתיקיית המצב |
| `npm run runner:check` | בדיקה של ההגדרות, של כל פרופיל (האם ה-CLI רץ ובאיזו גרסה, והאם מוגדר במחשב מפתח שגובר על תיקיית החשבון), של כל פרויקט (התיקייה קיימת, git) ושל ההתחברות |
| `npm run runner` | הפעלה עד Ctrl+C |
| `node runner/runner.js logout` | התנתקות במחשב הזה |

אפשר להעביר `--config <file>` או להגדיר `TASK_MANAGER_RUNNER_CONFIG`; ברירת המחדל היא `runner/runner.config.json`.

### ההגדרות (`runner.config.json`)

| שדה | ברירת מחדל | משמעות |
|-----|-----------|--------|
| `runnerName` | שם המחשב | השם שמוצג בלוח (באנגלית - הוא מודפס בקונסולה) |
| `supabaseUrl`, `supabaseAnonKey` | מ-`src/config.js` אם יש בו ערכים | אותם ערכים שהלוח משתמש בהם (ציבוריים; ההגנה היא RLS) |
| `stateDir` | `%LOCALAPPDATA%\task-manager-runner` | התחברות, `state.json`, לוגים, worktrees |
| `maxParallelJobs` | 2 (1-8) | כמה אייג'נטים במקביל |
| `jobTimeoutMinutes` | 60 (1-480) | אחרי זה הריצה נעצרת ומדווחת כנכשלת |
| `profiles.<name>` | | פרופיל = מנוע + חשבון + תיקיות מותרות |
| `projects[]` | | `{ key, name, profile, path, baseBranch?, isolation? }` |

שדות פרופיל:

| שדה | למי | משמעות |
|-----|-----|--------|
| `engine` | שניהם | `claude` או `codex` |
| `label` | שניהם | התווית בלוח ("עבודה", "אישי") |
| `allowedRoots` | שניהם | **התיקיות היחידות** שהפרופיל רשאי לעבוד בהן |
| `cloudReport` | שניהם | `minimal` (ברירת מחדל) או `full` |
| `command`, `model`, `worktreesDir` | שניהם | ה-CLI (ברירת מחדל: שם המנוע), מודל, איפה ליצור את תיקיות העבודה |
| `claudeConfigDir` | claude | ה-`CLAUDE_CONFIG_DIR` של החשבון (ריק = `~/.claude`) |
| `permissionMode` | claude | `acceptEdits` (ברירת מחדל), `auto`, `dontAsk`, `plan`, `manual`. `bypassPermissions` נחסם |
| `allowedTools`, `disallowedTools` | claude | כללי כלים, למשל `Bash(npm test *)`. ברירת המחדל של disallowed: `Bash(git push *)` |
| `codexHome` | codex | ה-`CODEX_HOME` של החשבון (ריק = `~/.codex`) |
| `sandbox` | codex | `workspace-write` (ברירת מחדל) או `read-only`. `danger-full-access` נחסם |

שדות פרויקט: `key` (אותיות קטנות, ספרות, `-`, `_`, עד 40 - זה מה שהלוח שומר), `path` (מוחלט), `baseBranch` (הענף שממנו נפתח ענף חדש; ברירת מחדל `HEAD`), `isolation`: `worktree` (ברירת מחדל - תיקייה וענף לכל משימה) או `none` (האייג'נט עובד ישירות בתיקיית הפרויקט; גם לתיקייה בלי git).

### ההפרדה בין עבודה לאישי (`validateConfig`)

הראנר לא עולה אם:
- לשני פרופילים יש תיקיות מותרות חופפות (אחת בתוך השנייה, בלי הבדל בין אותיות גדולות וקטנות ב-Windows);
- פרויקט לא נמצא בתוך התיקיות של הפרופיל שלו;
- ה-`worktreesDir` של פרופיל נמצא בתוך התיקיות של פרופיל אחר;
- לשני פרופילים עם אותו מנוע אין תיקיות חשבון מפורשות ושונות (`claudeConfigDir` / `codexHome`) - אחרת שניהם רצים עם אותו חשבון;
- יש מפתח פרויקט כפול, הרשאות עקיפה (`bypassPermissions`, `danger-full-access`), או כללי כלים עם תווים שמעטפת Windows מרחיבה.

עבודה מהענן מציינת רק מפתח פרויקט. הנתיב, המנוע והחשבון נקבעים רק בהגדרות המקומיות, ולכן פרויקט עבודה תמיד רץ עם פרופיל העבודה, ותיקייה שלא מופיעה בהגדרות לא הופכת לתיקיית עבודה של אייג'נט.

הסביבה של כל אייג'נט מנוקה (`agentEnvironment`): משתני החשבון והמפתחות של המנוע האחר מוסרים, ו-`CLAUDE_CONFIG_DIR` / `CODEX_HOME` נקבעים רק מהפרופיל (משתנה גלובלי כזה מוסר). מפתחות של המנוע עצמו (`ANTHROPIC_API_KEY` וכדומה) גוברים על תיקיית החשבון, ולכן `runner:check` מזהיר כשהם מוגדרים במחשב.

**מה ההפרדה לא מכסה:** התיקיות המותרות קובעות איפה האייג'נט עובד ובאיזה חשבון, לא מה הוא יכול לקרוא בדיסק. ה-sandbox של Codex, למשל, מאפשר קריאה בכל מקום, כך שאייג'נט אישי שמקבל הוראה מתאימה (גם דרך prompt injection) יכול לקרוא ריפו של העבודה. הפרדה מלאה דורשת להריץ את הפרופיל האישי תחת משתמש Windows נפרד, בלי הרשאה לתיקיות העבודה.

### מחזור החיים של עבודה (`worker.js`)

1. **הפעלה**: נעילה (`runner.lock` בתיקיית המצב, עם מזהה התהליך - ראנר שני עם אותה תיקייה לא עולה; נעילה של תהליך שכבר לא קיים נלקחת), שחזור ההתחברות (אם צריך לרענן אותה והרשת עוד לא עלתה - ניסיון כל 30 שניות, עד 20 פעמים), heartbeat (אם הטבלאות לא קיימות - הודעת שגיאה ויציאה), עבודות שנשארו `running` מהפעלה קודמת מסומנות `failed` ("הראנר הופעל מחדש באמצע העבודה"), מחיקת עבודות ישנות, האזנה ל-realtime (מסונן לפי `runner_id`), בדיקה כל 15 שניות ו-heartbeat כל דקה.
2. **בדיקת התור**: קודם ניסיון חוזר לדיווחים שנכשלו (רשת), אחר כך העברת בקשות עצירה לעבודות שרצות, ואז מעבר על העבודות שבתור לפי הסדר. עבודה לפרויקט שלא מוגדר כאן, או עם הודעה ריקה או ארוכה מדי, נדחית עם הסבר. עבודה של משימה שכבר רצה לה עבודה מחכה, וכך גם עבודה של פרויקט עם `isolation: none` שכבר רץ בו משהו. התפיסה (`claimJob`) מותנית ב-`status = 'queued'`. אם העצירה התחילה בזמן שהתפיסה הייתה בדרך, העבודה מוחזרת כנכשלת במקום להישאר "רצה".
3. **שיחה ותיקייה** (`ensureConversation`): לכל משימה בכל פרויקט (`<project>::<task>`) נשמרים ב-`state.json` המנוע, הפרופיל, מזהה השיחה (`sessionId`: מזהה ש-Claude מקבל מראש, או ה-thread של Codex מהתשובה הראשונה), האם השיחה כבר התחילה, התיקייה, הענף וה-commit שממנו התחילה. אם המנוע, הפרופיל, תיקיית החשבון או תיקיית העבודה השתנו - מתחילה שיחה חדשה.
4. **הרצה** (`runAgent`): ההודעה עוברת דרך stdin, אף פעם לא בשורת הפקודה. להודעה הראשונה בשיחה נוספות הנחיות דיווח: סיכום קצר בעברית, שאלה ברורה אם צריך החלטה, בלי push / merge / פריסה, ובמצב `minimal` גם בלי קוד בסיכום. הפלט המלא נכתב ל-`logs/<jobId>.log`.
5. **שיחה שאי אפשר להמשיך**: כשהמשך של שיחה נכשל בלי שום תשובה (למשל Claude כבר מחק את התמליל, או שתיקיית החשבון השתנתה), מתחילה שיחה חדשה באותה תיקייה, פעם אחת. אם היא באמת התחילה, היא נשמרת, ובראש הסיכום מופיעה הערה שייתכן שחסר לאייג'נט הקשר. אם גם היא נכשלה (למשל אין רשת), השיחה הקודמת נשמרת לפעם הבאה.
6. **דיווח**: `done` / `failed` / `cancelled`, סיכום (`shapeSummary`), שגיאה, ענף, תיקייה ומספר קבצים שהשתנו מאז תחילת המשימה (כולל קבצים חדשים). דיווח שנכשל בגלל הרשת נשמר בזיכרון ונשלח שוב בבדיקה הבאה. אם העבודה כבר נסגרה בלוח, הדיווח לא נרשם, ובקונסולה מופיעה אזהרה.
7. **עצירה** (Ctrl+C): אין יותר תפיסת עבודות, הבדיקה שבאמצע מסתיימת, האייג'נטים שרצים נעצרים ומדווחים כ-`failed` ("הראנר נעצר באמצע העבודה").

### המנועים (`engines.js`)

**Claude Code**: `claude -p --output-format json --permission-mode <mode> --permission-prompts none` עם `--session-id <uuid>` להודעה הראשונה ו-`--resume <uuid>` להמשך, `--allowedTools` / `--disallowedTools` / `--model`, ו-`CLAUDE_CONFIG_DIR` לפי הפרופיל. `--permission-prompts none` אומר שכל פעולה שהייתה מבקשת אישור נדחית, כי אף אחד לא יושב מול המחשב. התשובה היא אובייקט ה-JSON האחרון בפלט (`result`, `session_id`, `is_error`). שיחה שלא התחילה (אין JSON) מקבלת מזהה חדש לניסיון הבא, כדי שלא תהיה התנגשות עם session שנוצר רק בחלקו.

**Codex**: `codex exec --json -o <file> -c sandbox_mode=<sandbox> -c approval_policy=never [-m model] -` (או `codex exec resume ... <thread> -`), עם `CODEX_HOME` לפי הפרופיל, ו-`--skip-git-repo-check` כשהתיקייה לא ב-git. מזהה ה-thread נלקח מאירוע `thread.started`, והתשובה מהקובץ של `-o` (או מאירוע `agent_message` האחרון). ריצה נחשבת כנכשלת רק לפי קוד יציאה שונה מ-0 או `turn.failed`. אירוע `error` לבד (למשל "Reconnecting...") רק מספק את הודעת השגיאה.

**הפעלת התהליך** (`runProcess`): ב-Windows, עטיפות ה-npm (`claude.cmd`, `codex.cmd`) נקראות כדי למצוא את היעד האמיתי (`claude.exe`, או `node codex.js`), כך שאין מעטפת באמצע. רק אם זה לא מצליח יש מעבר למעטפת, וכל ארגומנט מצוטט ונבדק. פקודה שלא נמצאת ב-PATH לא מופעלת בכלל, כי אחרת Windows היה עלול להריץ קובץ באותו שם מתיקיית העבודה. timeout ועצירה הורגים את כל עץ התהליכים (`taskkill /T /F`, או קבוצת תהליכים ב-POSIX).

### מה עולה לענן

| | `minimal` (ברירת המחדל - פרויקטים של העבודה) | `full` (פרויקטים אישיים) |
|---|---|---|
| הנחיה לאייג'נט | לסכם במילים, בלי קוד, סודות או פרטים מזהים | סיכום רגיל |
| בלוקי קוד ב-```...``` וקוד inline ארוך | מוחלפים ב-"[קוד הושמט...]" | נשארים |
| אורך הסיכום | עד 1,500 תווים | עד 8,000 תווים |
| אורך השגיאה | עד 500 תווים | עד 1,000 תווים |

בכל מקרה עולים גם הענף, נתיב התיקייה ומספר הקבצים שהשתנו. הפירוט המלא נשאר רק בלוג המקומי. מה שהמשתמש כותב בלוח (ההודעה עצמה, כותרת ותיאור המשימה) נשמר בענן כמו כל משימה.

### תיקיית המצב

`%LOCALAPPDATA%\task-manager-runner` (או `~/.task-manager-runner`): `auth.json` (ה-session, כולל refresh token - סוד; ב-POSIX ההרשאות הן 600, וב-Windows התיקייה בפרופיל המשתמש; הכתיבות אליו בתור אחד), `runner.lock`, `state.json`, `runner.log` (כל שורות הקונסולה), `logs/<jobId>.log` (נמחקים אחרי 30 יום), `tmp/`, `worktrees/<profile>/<project>/<task>`.

### הקונסולה

כל ההודעות באנגלית, בצבעים: מידע ציאן, הצלחה ירוק, אזהרה צהוב, שגיאה אדום (`console-log.js`). שמות בעברית (שמות פרויקטים, תוויות) לא מודפסים בקונסולה.

## מגבלות

- הראנר עובד רק כשהמחשב דולק והתוכנית רצה. כדי שיעלה לבד אפשר להגדיר משימה ב-Task Scheduler (במדריך).
- אין אישורים אינטראקטיביים: מה שלא מותר ב-`permissionMode` / `allowedTools` (או ב-sandbox של Codex) נדחה, והאייג'נט מדווח שלא הצליח.
- הודעה אחת בכל פעם לכל משימה. עבודות של משימות שונות רצות במקביל עד `maxParallelJobs`.
- הלוח מציג עד 300 עבודות אחרונות.
- מי שמשתלט על החשבון בלוח יכול לשלוח הוראות לאייג'נטים במחשב. ההגנות: רק פרויקטים מההגדרות המקומיות, ההרשאות של האייג'נט, וסיכום מצומצם בפרויקטים של העבודה. כדאי סיסמה חזקה וייחודית לחשבון.
- חסימת `git push` ב-`disallowedTools` וההנחיה לא לדחוף הן שכבה רכה: אייג'נט שמותר לו להריץ סקריפטים (למשל `npm run`) יכול לערוך סקריפט או hook ולהריץ דרכו כל פקודה. לכן התבנית לא מתירה `npm run *`. הגנה אמיתית מ-push היא ברמת ההרשאות של ה-git במחשב.
- במצב `minimal` עולים לענן גם נתיב תיקיית העבודה (בשביל "פתיחה ב-VS Code") ושגיאות מקוצרות של ה-CLI.
- ההפרדה בין הפרופילים לא מגבילה קריאה מהדיסק (ראו למעלה).
- ה-merge של הענף נעשה ידנית (ב-VS Code או בגיט).
